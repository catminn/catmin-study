# NPC testimony and causal continuity — author acceptance v1 (spoiler-free)

**Scope.** This is a narrative-author contract and a small synthetic reference model, not the production NPC engine or the private first-world story. All identifiers and copy in the accompanying files are invented test placeholders. The actual first-world character identities, motives, routes, revelations and dialogue must remain in the authorized private authoring package. ChatGPT owns the behavioral semantics and DM acceptance; Claude owns authenticated event provenance, persistence, D1 transactions, APIs and engine integration.

## Invariants for a playable NPC

1. **Presence before speech.** The NPC can respond in a scene only when the authoritative committed location matches the player's scene and availability is `available`. A narrator must not invent a remote conversation or use an unseen character to deliver a needed clue. Unavailable or absent characters may produce a neutral absence response, never an explanation of their secret reason.
2. **Claims are not facts.** Track what an NPC has *heard* separately from what the NPC has *verified*. Track the player's heard claims separately from the player's confirmed discoveries. Repeating a rumor never promotes it to verified knowledge; the model's confidence or narrative eloquence changes no tier. Player discovery does not automatically update NPC knowledge, and vice versa.
3. **Conversation requires a committed encounter.** An ASK, preview, drafted line, suggested route or declined conversation has no effect on relation, knowledge, location, availability or story cursor. A committed player-to-NPC communication can create a heard claim, not an NPC-confirmed fact. NPC-to-player testimony can create a heard claim only if the NPC actually knows or has heard the claim and the audience permits it.
4. **Route memory persists after convergence.** Both legitimate branches can arrive at the same scene while retaining different committed relationship bands and route traces. Subsequent NPC behavior can react to the difference without disclosing a branch's hidden consequences. A later scene may not overwrite history to make both routes equivalent.
5. **Disclosure is separately authorized.** Server-private knowledge is never copied into a public response merely because the NPC knows it. Public dialogue must come from an independently reviewed copy slot whose gate matches the current committed state. The reference projection returns only neutral availability and approved synthetic text; it does not return NPC IDs, fact IDs, route traces, claim arrays, private profiles or commit logs.
6. **Commit authority is external.** The reference accepts events marked `source: server` and `status: committed` only to demonstrate the authoring rule. Those strings are *not* authentication. Claude's real engine must derive trusted event origin, session pin, version, provenance, commit ID and audience from server-owned state; never trust client or model declarations. Effects must be atomic, idempotent and scoped to the correct world/revision/session.
7. **Learning remains optional.** A player may ask for an explanation or decline a MATH 1920 application without freezing the NPC or forcing a quiz. Verified learning evidence may inform a voluntary action but cannot manufacture NPC knowledge, consent or a successful world event.

## Commit-ID ledger safety (synthetic reference)

A server-committed event ID must match \`^[a-z][a-z0-9._-]{0,79}$\` before any NPC state transition. This rejects empty, oversized, malformed and prototype-magic keys (notably \`__proto__\`) that a plain-object replay ledger cannot reliably record. Rejected committed IDs return the fixed \`not_committed\` code and preserve the original state. Valid IDs are recorded once, replay without a second mutation, and cannot be reused for different event content. ASK and preview remain no-op even if they carry a malformed ID: they never write to the ledger.

Run \`node --test test/npc-event-id-safety.test.mjs\` for eight new synthetic cases, alongside the original NPC reference suite. These are author-side invariants, not proof of a production exploit or a request to alter live Worker/D1 behavior.

## Player-to-NPC knowledge provenance (synthetic reference)

A committed `player_told_npc` event is eligible only when the player already holds the referenced fact as a heard claim or a confirmed discovery, the fact is explicitly player-accessible, and the NPC is available in the same scene. A server-only fact is never a valid player testimony source, even if a malformed or forged player knowledge array contains its ID. An unknown fact returns `fact_unknown`; a private audience returns `audience_denied`; a known but unlearned fact or malformed player knowledge arrays return `player_cannot_testify`. Rejection preserves the input state and commit ledger. Accepted player testimony grants the NPC a **heard** claim only; it never promotes the NPC to confirmed knowledge. Player knowledge does not teleport to the NPC, and NPC knowledge does not teleport to the player.

The player may learn a public claim through a committed `npc_told_player` event or have a public fact independently verified via `fact_verified` with `subject: player`. This reference deliberately has no general rumor-invention action: a player asserting an unfamiliar fact requires a separately authored and reviewed action type, not a fabricated `player_told_npc` fact reference. ASK and preview remain non-committing. Eight synthetic regression tests in `test/npc-player-knowledge-provenance.test.mjs` cover unlearned and private claims, heard-versus-confirmed tiers, source isolation, malformed knowledge, remote NPCs and ASK/preview. Run `node --test test/npc-testimony-reference.test.mjs test/npc-knowledge-copy-gates.test.mjs test/npc-event-id-safety.test.mjs test/npc-player-knowledge-provenance.test.mjs` (Node 22). These are author-reference invariants, not a production server vulnerability finding or permission to import private content.

## Persisted NPC state shape — fail-closed author reference

Before a committed event, ASK/preview or approved dialogue projection, the synthetic reference validates persisted state shape. Malformed NPC/player records, knowledge collections, versions, locations, availability or replay ledgers return fixed `state_invalid` without mutation. Dialogue projection returns only `{available:false,text:null}` for corrupt state, even when neutral copy is approved. Player knowledge arrays must contain unique, player-accessible known fact IDs; NPC knowledge arrays contain unique known IDs. Ledger keys use safe event-ID grammar and values are strings. Invalid state takes precedence over per-action fact/audience errors; two earlier provenance fixtures now expect `state_invalid` for forged private or malformed knowledge arrays.

The fourteen cases in `test/npc-corrupt-state-fail-closed.test.mjs` cover malformed records and collections, version, location, ledger, privacy, ASK/preview and healthy replay. Run with other NPC reference tests using Node 22. This is not a production storage migration or proof of a real Worker/D1 defect. Real persistence and recovery behavior belong to Claude; private first-world import remains blocked.

## Persisted route and commit-count continuity (synthetic reference)

The author-side NPC state validator now checks **causal coherence**, not only field types. At the starting fork, the trace is absent, the relationship is neutral and the NPC remains at the fork. After either committed branch, its route trace and relationship must match that branch while the NPC remains at the fork. After convergence, the same trace and relationship persist and the NPC is located in the joined scene. A saved scene, trace, relation or NPC location that contradicts these stages is `state_invalid`, with no commit or approved dialogue. Availability and knowledge may change independently through valid committed events.

The replay ledger must contain exactly one valid commit entry per state version; missing or extra entries are treated as corrupt persistence. This count check is a **consistency guard**, not cryptographic provenance: a fabricated ledger with matching counts is not authenticated. Real event authority, transactional persistence and recovery remain Claude's responsibility. The eighteen synthetic tests in `test/npc-route-state-integrity.test.mjs` cover both routes, convergence, legal availability changes, mismatched snapshots, count drift and idempotent replay. These checks neither authorize production changes nor reveal first-world content.

## Public NPC copy shape and display safety (synthetic author preflight)

An author-approved flag in a synthetic policy is not an authorization or proof of real editorial approval. Before the reference projects NPC dialogue, and before the route bridge accepts a route's dialogue, both now apply the same pure `npcPublicCopySafe` preflight. Eligible copy is an object containing only `text`, `relation`, `approved`, and optional `requiresNpcKnowledge`. `approved` must be exactly true, `relation` must use the safe author ID grammar, and `text` must be a nonblank string of at most 1200 Unicode code points. Reject control and bidirectional override characters, zero-width camouflage characters, director placeholders starting with `⟦DG:`, extra metadata, non-string text, and malformed knowledge-gate shapes. Ordinary Unicode and emoji (including ZWJ sequences) remain usable. A well-shaped knowledge gate must still pass the existing NPC knowledge-tier and fact-policy checks before dialogue can appear.

The reference returns only `{available:true,text:null}` for unsafe copy while an NPC is present, or `{available:false,text:null}` if absent/unavailable/corrupt; it never returns a malformed object-valued copy. The bridge emits only fixed `dialogue_unapproved` diagnostics and cannot echo private copy or identifiers. This is **syntactic preflight, not spoiler detection**: a grammatically valid line can still reveal secrets semantically, and real text still needs private per-field review and Catherine's authorization. The same rule is not an instruction to change production projection or migrate existing data without engineering review.

Run `node --test test/npc-public-copy-safety.test.mjs test/npc-public-copy-integration.test.mjs` with Node 22. These synthetic tests cover public-copy shape, invisible/control/placeholder hazards, route-bridge rejection, and ordinary knowledge-gated dialogue. They do not exercise the production Worker/D1 renderer, real NPC identities, model narration, or real review provenance.

## Ordered synthetic route-ledger consistency

A matching ledger **count** no longer suffices to validate a persisted route. The author reference now parses its synthetic committed-event fingerprints in insertion order and requires exactly one matching `route_committed` before the route stage, followed by exactly one `scene_entered` before reunion. A missing, reordered, conflicting, malformed or cross-scope fingerprint fails closed before any NPC line is projected or another event is committed. Legal availability and knowledge events can occur around the route without erasing its history. Diagnostics remain fixed; the checker never returns fingerprint text.

Run `node --test test/npc-route-ledger-provenance.test.mjs` for synthetic positive and negative cases. This is **not** an authenticated log: a fabricated fingerprint with a plausible event shape is not cryptographic proof that an event occurred. Claude owns trusted Worker/D1 event provenance, transaction order and recovery. Do not import the first formal world without private review and Catherine's explicit authorization.


## Persisted knowledge and availability derived from synthetic history

The author-side state validator now reconstructs NPC and player **heard** and **confirmed** fact sets from the ordered synthetic event fingerprints, instead of accepting a plausible snapshot merely because its fact IDs exist in the policy. A persisted knowledge tier is valid only when the matching committed verification or eligible testimony appears in history. NPC-to-player and player-to-NPC testimony must occur during an available, co-located encounter and require prior knowledge on the speaker's side. Player verification and any testimony reaching the player require a player-accessible fact. The validator also reconstructs availability changes and compares the resulting availability with the persisted NPC state. Repeated verification is idempotent; legitimate knowledge survives route convergence.

Run \`node --test test/npc-knowledge-ledger-integrity.test.mjs\` (17 synthetic positive/negative cases). An invalid snapshot fails closed before ASK/preview, a further commit or an approved dialogue projection. This is **not** a trusted event source or a production migration: a forged but internally consistent ledger remains possible in the reference. Claude must authenticate server-owned event order, audience and persistence in Worker/D1 using placeholder content. No formal-world import or enforce-mode change is authorized.
