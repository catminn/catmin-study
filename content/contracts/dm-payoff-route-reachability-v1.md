# DM learning payoff — both-route world reachability preflight v1

**Boundary:** Public, spoiler-free, synthetic author-side preflight. All test identifiers are invented. It is neither a production gate nor an authorization to import, merge, deploy, expose story content, or modify a save.

The existing `validateDmLearningPayoff` verifies that a DM lesson can be associated with one registered optional world action. That action can still be disconnected from the playable map, reachable only on one committed branch, or reachable only *after* the declared story goal. Such a link does not demonstrate that the player can apply the lesson while following both story routes.

`validateDmPayoffRouteReachability(flow, actions, worldGraph, proof)` checks a **separate, complementary condition**. It requires exactly two proof entries covering the two committed choice routes by `routeBeatId` and `traceRef`. Each entry declares an author-supplied world entry scene and goal, plus the optional `actionKey`, ungated `baseActionKey`, and its `worldFrom`/`worldTo` edge. The registered action must use the proof's chapter skill, match the source/destination edge, and be reachable from that route's entry **before** the goal. Its destination must be able to reach the goal. World cycles are permitted; the reachability search terminates using a visited set. Disconnected or malformed world nodes, missing references, duplicate route proofs, revision mismatches, and unreviewed proof fields fail closed. Diagnostics contain fixed codes and counts, never user-supplied identifiers or text.

Proof shape: `schemaVersion:"dm-payoff-route-reachability-v1"`, `synthetic:true`, `worldId`, `dmRevision`, `dungeonId`, `actionRevision`, `lessonBeatId`, `applicationRef`, `skillId`, `chapterIndex`, and exactly two `routes` entries. Each route entry has exactly `routeBeatId`, `traceRef`, `entrySceneId`, `goalSceneId`, `actionKey`, `baseActionKey`, `worldFrom`, `worldTo`. The DM revision and action revision remain distinct namespaces; the proof is not a trusted identity attestation. The same optional action after a convergence is allowed for both routes.

Run `node --test test/dm-payoff-route-reachability.test.mjs` with Node 22. This is an **additional check**, not a replacement for `validateDmBeatFlow`, `validateDmKnowledgeAlignment`, `validateSkillActionBindings`, or `validateDmLearningPayoff`; all must independently pass. A supplied route→world-entry mapping is an untrusted author assertion, not evidence that the runtime will take that route. A registered `baseActionKey` is compared to its declaration, but the existence of an ungated server action is not proven by this graph. The check cannot prove mathematical causality, narrative quality, a visible learning payoff, server event authorization, or actual model/Worker/D1 behavior. Those remain for private editorial review and Claude's placeholder-content engineering tests. The first formal world remains **DO-NOT-IMPORT** pending private field-by-field review and Catherine's explicit in-person authorization.

## Ambiguity and graph-projection hardening

This author preflight fails closed on duplicate DM beat IDs, duplicate skill IDs or chapter assignments, ambiguous optional/base action keys, unknown action advantage types, and unreviewed action-registry fields. Synthetic binding entries have exactly `actionKey`, `baseActionKey`, `skillId`, `from`, `to`, and `advantage` (`evidence_option` or `risk_context`). This does **not** replace the separate four-skill/four-binding `validateSkillActionBindings` preflight.

The reachability graph is an **explicitly reviewed projection**: its root has only `nodes`, and each node has exactly `id` and `next`. Hidden `requiresStudy`, `locked`, or other gating metadata is rejected rather than silently interpreted as an open edge. This does **not** prove that the runtime lacks server-side gates; the author must separately reconcile the projection with runtime behavior using synthetic Worker/D1 tests. All diagnostics remain fixed, non-echoing codes.
