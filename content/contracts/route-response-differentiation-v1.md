# Route response differentiation — spoiler-free author acceptance v1

This optional, synthetic author-side preflight complements `validate-route-consequence-outline.mjs`. That existing graph validator proves that each chosen branch has a conditional acknowledgement on every continuation; it does **not** prove the authored acknowledgement is distinguishable from a sibling choice's acknowledgement. This check closes that narrower false positive.

`validateRouteResponseDifferentiation(outline, plan)` first validates the existing consequence outline, then requires exactly one approved, nonblank response copy for every branching edge's opaque `impactKey`. For exits from the **same choice beat**, normalized text must differ (Unicode NFKC, whitespace collapsed, case-insensitive); separate choice beats may legitimately reuse text. Unrecognized fields, duplicate or missing keys, unapproved copies, and empty text fail closed with fixed diagnostic codes. The author may inspect private copy in memory, but the function never returns copy, impact keys, text hashes, or identifiers. The repository contains only invented demo copy.

The plan schema is exactly `{schema:'route-response-differentiation-v1',responses:[{impactKey,approved,copy}]}`. Run `node --test test/route-response-differentiation.test.mjs` in Node 22 for the synthetic acceptance suite. Distinct text is a necessary but insufficient condition for meaningful consequences: this cannot judge semantic differences, prose quality, whether the conditional line actually renders, or whether an NPC remembers choices. It does not authorize any production change, private content import, or gameplay gate. First formal world remains **DO-NOT-IMPORT** pending private review, real Worker/D1 tests and Catherine's explicit in-person approval.

## Invisible text and control-character safety

Branch responses must be visibly distinguishable. For comparison only, the author preflight ignores invisible formatting characters including zero-width separators/joiners, soft hyphens, word joiners and Unicode variation selectors, in addition to existing NFKC/case/whitespace normalization. This conservative check may reject two intentionally different emoji presentations as insufficiently distinct; authors can provide genuinely different prose. A response made solely of invisible characters is blank. Bidi override/isolate/direction controls and non-whitespace C0/C1 control characters are rejected with the fixed `response_invalid` code; ordinary tabs and line breaks remain allowed. This is a static author-side safeguard, not Unicode confusable detection, semantic review, rendering security or a production sanitization layer. Synthetic regressions live in `test/route-response-invisible.test.mjs`.

## Unicode default-ignorable response comparison

The earlier hand-maintained invisible-character list missed other default-ignorable code points, including Hangul filler and Khmer inherent vowel signs. These could make two visibly identical sibling replies pass the distinct-response check, or make a response containing only invisible characters appear nonblank. The author-side comparison now uses the Unicode `Default_Ignorable_Code_Point` property after NFKC normalization, rather than a partial enumeration. Ordinary visible text and emoji ZWJ sequences remain eligible; intentionally different emoji presentation styles alone may be treated as equivalent.

Five additional synthetic regressions cover three previously missed invisible-codepoint families, invisible-only text, and visible emoji. The original implementation incorrectly accepted four of the five cases. The patched validator passed all five and the existing 29 route-response tests in an isolated V8 evaluation of the exact GitHub source (34/34). This is not native Node CI, visual rendering verification, semantic differentiation, or approval of private narrative content.

## Reserved director delimiters and UTF-16 validity

Approved route responses are player-facing copy. In addition to control-character checks, the author preflight now rejects either reserved director-expansion delimiter (`⟦` or `⟧`) anywhere in a response, including unmatched delimiters, and rejects unpaired UTF-16 surrogates. This aligns the response boundary with the NPC public-copy safety preflight: a response's `approved:true` flag is not permission to embed director-only markers. Valid Unicode characters, including supplementary-plane emoji and joined emoji sequences, remain allowed. Violations return only `response_invalid`, without echoing the supplied text. Synthetic regressions are in `test/route-response-differentiation.test.mjs`.

This is a static authoring safeguard. It does not prove the runtime renderer or a private world package is safe, and it does not authorize an import.
